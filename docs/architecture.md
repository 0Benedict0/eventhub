# EventHub — Architecture

```
React (Vite, TS)  ──REST (axios)──▶  Spring Boot Controller ──▶ Service ──▶ Repository ──▶ PostgreSQL
                                              │                       │
                                              ▼                       ▼
                                        Redis (кеш GET /events)   @Version (optimistic lock)
                                              │
                                              ▼
                                   ReminderScheduler (@Scheduled, щодня 9:00)
```

## Конкурентне бронювання (найважливіше рішення в проєкті)

Проблема: якщо на подію залишилось 1 місце, і два користувачі одночасно
тиснуть "Забронювати", наївна реалізація (`SELECT availableSeats` →
перевірка в Java → `UPDATE`) дозволить обом пройти перевірку одночасно —
класичний **lost update** race condition, подія продасть на одне місце
більше, ніж є.

Рішення — **optimistic locking** через `@Version` на `Event`:
1. Обидва запити читають `Event` з однаковою версією (наприклад, `version=5`).
2. Перший `UPDATE ... WHERE id=? AND version=5` проходить, версія стає `6`.
3. Другий `UPDATE ... WHERE id=? AND version=5` не знаходить жодного рядка
   (версія вже `6`) → Hibernate кидає `OptimisticLockingFailureException`.
4. `BookingService.book()` ловить цей виняток і **повторює спробу** ще до
   3 разів, перечитуючи вже актуальний стан — замість одразу відмовляти
   користувачу.

Чому не pessimistic lock (`SELECT ... FOR UPDATE`)? Той підхід тримав би
рядок заблокованим для ВСІХ читачів (включно з тими, хто просто переглядає
сторінку події) на час транзакції — при високому трафіку це вузьке місце.
Optimistic lock дешевший, поки конфлікти рідкісні (що true для більшості
подій — конкуренція за останні місця буває лише в піку).

### Важлива деталь реалізації
Транзакційна частина бронювання винесена в окремий Spring-бін
(`BookingTransactionExecutor`), а не залишена private-методом у
`BookingService`. Причина — **self-invocation problem**: якби
`@Transactional`-метод викликався через `this.method()` в межах того самого
класу, Spring AOP-проксі не спрацював би, і винятки не спричиняли б
справжній rollback. Цей нюанс — типова причина багів, які "працюють на
тестах, але не в проді", тому виправлений навмисно, а не залишений як
демонстрація помилки.

## Redis-кеш

`GET /api/events` (пошук/список) кешується на 60 секунд — найчастіший
запит на публічній сторінці. Ключ кешу враховує всі параметри фільтрації,
щоб різні комбінації (`keyword`, `categoryId`, дати, сторінка пагінації)
не витісняли одна одну. Кеш явно інвалідується (`@CacheEvict`) при
створенні/редагуванні події та при бронюванні — щоб кількість вільних
місць не "застрягала" застарілою довше, ніж на TTL.

## Scheduled reminder

`ReminderScheduler` щодня о 9:00 знаходить події, що відбудуться завтра,
і "надсилає" нагадування всім з підтвердженим бронюванням. На відміну від
Kafka-подій у ShopHub (тригер — дія користувача), тут тригер — **час**,
що є іншим типовим патерном фонової обробки в backend-системах.
